Working note: one policy, several clients +

How can shared guidance reach different coding agents without pretending they load instructions alike? I give a rule one canonical owner, then adapt its delivery to each client.

My public dotfiles document configuration ownership. The Cursor rule renderer expands a marker and replaces rendered output atomically. Its tests cover repeated runs, invalid inputs, migration, and replacement failure.

This trades a small adapter and its tests for fewer competing copies of policy. A correctly rendered file still does not prove an agent loaded or followed it. See the verification boundary or return to the harness topic.

Working note: what did we actually verify? +

A file can exist without being discovered, loaded, or followed. I separate source, installation, fresh-session loading, and exercised behavior.

The public verification guide names those boundaries. A Pi startup check examines effective prompts and skill discovery in fresh workspaces. It needs an installed Pi package; its source is not evidence of a current passing run.

A passing startup check would establish loading under those test conditions, not future model compliance. That is why review and recovery remain separate from setup.

Working note: why this site stays small +

What should work before a script runs? On this site, links, disclosures, and the relationship directory live in the HTML response.

The homepage source contains the reading paths. The enhancer adds panel selection, fragment-aware focus, titles, and interruptible decorative motion. Browser tests check navigation and no-script reading.

Native HTML reduces runtime machinery for this content-led site. It does not remove the need to test focus, history, mobile layout, and reduced motion. Follow the artifact to production.

Working note: deploy in the right order +

A new route may refer to an artifact object absent from the previous build. Deleting old objects before CloudFront changes can break the site.

The delivery decision replaces independent pipelines. Recipes build and check, save an infrastructure plan, stage files, apply, then wait. Finally, they clean obsolete objects and invalidate caches. S3 access and distribution routing remain explicit Terraform rather than third-party modules.

This favors inspection and ordering over a faster website-only pipeline. Staging is not atomic; mocked infrastructure tests cannot prove live edge propagation. Return to the site's implementation.
